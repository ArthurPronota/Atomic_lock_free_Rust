# Atomic lock-free в Rust: описание на основе примера

## Что такое Atomic lock-free

**Atomic-типы** — это обёртки над примитивами, которые дают **lock-free операции** (без блокировок ОС). Они:

- используют **инструкции процессора** (например, `LOCK XADD`, `CMPXCHG`) для атомарности;
- **не блокируют** поток — нет мьютексов, нет системных вызовов;
- требуют **явного memory ordering** — вы сами указываете, какой уровень синхронизации нужен.

## Разбор примера

```rust
use std::thread;
use std::sync::atomic::{AtomicUsize, Ordering};

static CNT: AtomicUsize = AtomicUsize::new(0);

fn main() {
    let handls = (0..4)
        .map(|_| {
            thread::spawn(move || {
                for i in 0..1000 {
                    CNT.fetch_add(1, Ordering::Release);
                }
            })
        })
        .collect::<Vec<_>>();

    for h in handls {
        h.join().unwrap();
    }

    println!("{}", CNT.load(Ordering::Acquire));   // 4000
}
```

Пошагово:

1. **`static CNT: AtomicUsize`** — глобальный атомарный счётчик, инициализирован `0` в **const-контексте** (`AtomicUsize::new` — `const fn`).
2. **4 потока**, каждый делает **1000 инкрементов** через `fetch_add`.
3. **`Ordering::Release`** на `fetch_add` — гарантирует, что записи **до** инкремента видны другим потокам **после** него.
4. **`Ordering::Acquire`** на `load` — гарантирует, что чтения **после** `load` видят записи, сделанные **до** `Release`.
5. **`.join()`** — ждём завершения всех потоков.
6. **`CNT.load(Acquire)`** — читаем финальное значение: **4000**.

**Важно:** `fetch_add` — **read-modify-write** операция, поэтому `Release` здесь **корректен** (для RMW можно использовать `Release`, `AcqRel`, `SeqCst`, но не `Acquire` в одиночку).

## Memory Ordering — что это

**Memory ordering** — это **правила переупорядочивания** операций компилятором и процессором. Без них:

- компилятор может **переставить** инструкции;
- процессор может **выполнить** их в другом порядке;
- кэши разных ядер могут **не видеть** изменения друг друга.

`Ordering` говорит: **какие перестановки разрешены**, а какие — нет.

## Пять уровней Ordering

### 1. `Relaxed` — только атомарность

```rust
CNT.fetch_add(1, Ordering::Relaxed);
```

- Гарантирует **только атомарность** самой операции.
- **Нет** барьеров — компилятор и CPU свободно переставляют операции вокруг.
- **Нет** синхронизации между потоками.
- **Когда использовать:** счётчики, статистика, где важен только финальный результат.

### 2. `Acquire` — для `load`

```rust
let value = CNT.load(Ordering::Acquire);
```

- **Запрещает** перестановку **последующих** чтений **перед** `load`.
- Операции **после** `load` **не могут** быть перемещены **до** него.
- Операции **до** `load` **могут** быть перемещены **после** (технически).
- **Когда использовать:** чтение флага, после которого идёт чтение защищённых данных.

### 3. `Release` — для `store`

```rust
CNT.store(42, Ordering::Release);
```

- **Запрещает** перестановку **предыдущих** записей **после** `store`.
- Операции **до** `store` **не могут** быть перемещены **после** него.
- Операции **после** `store` **могут** быть перемещены **до** (технически).
- **Когда использовать:** запись данных, затем установка флага.

### 4. `AcqRel` — для read-modify-write

```rust
CNT.fetch_add(1, Ordering::AcqRel);
```

- **Комбинация** `Acquire` и `Release`:
  - для **load**-части — как `Acquire`;
  - для **store**-части — как `Release`.
- **Применим только** для **read-modify-write** операций:
  - `fetch_add`, `fetch_sub`, `fetch_and`, `fetch_or`, `fetch_xor`;
  - `compare_exchange`, `compare_exchange_weak`;
  - `swap`.
- **Не используется** для простых `load`/`store`.

### 5. `SeqCst` — глобальный порядок

```rust
CNT.fetch_add(1, Ordering::SeqCst);
```

- Даёт **все** гарантии `Acquire`, `Release`, `AcqRel`.
- **Добавляет глобальный порядок**: все потоки согласованы в том, **в каком порядке** выполнялись `SeqCst`-операции.
- **Самый строгий** и **самый медленный**.
- **Когда использовать:** когда нужен **тотальный порядок** или **лень думать** (безопасный дефолт).

## Сводная таблица

| Ordering | Для чего | Барьеры | Синхронизация |
|---|---|---|---|
| `Relaxed` | Атомарность | Нет | Нет |
| `Acquire` | `load` | Запрещает перестановку **последующих** чтений вверх | С `Release` |
| `Release` | `store` | Запрещает перестановку **предыдущих** записей вниз | С `Acquire` |
| `AcqRel` | RMW | `Acquire` + `Release` | С `Acquire`/`Release` |
| `SeqCst` | Всё | Все + глобальный порядок | Глобальная |

## Паттерн Acquire/Release

Классический паттерн синхронизации:

```rust
// Поток 1 (производитель):
data = 42;                          // обычная запись
flag.store(true, Ordering::Release); // Release: data видна после flag

// Поток 2 (потребитель):
while !flag.load(Ordering::Acquire) {} // Acquire: ждём flag
println!("{}", data);               // видим data = 42
```

**Гарантия:** если потребитель увидел `flag == true` через `Acquire`, он **обязательно** увидит `data == 42`, записанную **до** `Release`.

## Почему в примере именно `Release`/`Acquire`

```rust
CNT.fetch_add(1, Ordering::Release);   // в потоках
CNT.load(Ordering::Acquire);           // в main
```

- `fetch_add` — **read-modify-write**, но используется `Release` (можно было `AcqRel` или `SeqCst`).
- `Release` гарантирует, что **все предыдущие записи** потока видны другим **после** инкремента.
- `load(Acquire)` в `main` гарантирует, что **все последующие чтения** видят записи, сделанные **до** `Release`.
- **Пара `Release`/`Acquire`** создаёт **happens-before** отношение: записи потока-производителя **видны** потоку-потребителю.

**Но:** для **простого счётчика** достаточно и `Relaxed` — важен только **финальный результат**, а не порядок.

## Когда `Relaxed` достаточно

```rust
static COUNTER: AtomicUsize = AtomicUsize::new(0);

// В потоках:
COUNTER.fetch_add(1, Ordering::Relaxed);

// В main:
COUNTER.load(Ordering::Relaxed);
```

- **Атомарность** гарантирована — не будет **потерянных** инкрементов.
- **Финальное значение** — корректно (`4000`).
- **Порядок** инкрементов **не важен**.
- **`Relaxed` быстрее** — нет барьеров памяти.

**Когда `Relaxed` НЕ подходит:**

- Нужно, чтобы **другие данные** были видны **после** операции.
- Нужен **порядок** между несколькими переменными.
- Паттерн «флаг + данные».

## Lock-free vs Mutex

| | Atomic | Mutex |
|---|---|---|
| Блокировка ОС | ❌ Нет | ✅ Да |
| Системные вызовы | ❌ Нет | ✅ Да (futex) |
| Скорость | ✅ Высокая | ⚠️ Средняя |
| Простота | ⚠️ Сложнее | ✅ Проще |
| Memory ordering | Явный | Неявный |
| Deadlock | ❌ Невозможен | ✅ Возможен |
| Для чего | Простые примитивы | Сложные структуры |

## Итог

- **Atomic-типы** дают **lock-free** операции через **инструкции процессора**.
- **Memory ordering** — правила переупорядочивания операций.
- **Пять уровней:**
  - `Relaxed` — только атомарность;
  - `Acquire` — для `load`, запрещает перестановку **последующих** чтений;
  - `Release` — для `store`, запрещает перестановку **предыдущих** записей;
  - `AcqRel` — для RMW (`fetch_add`, `compare_exchange`);
  - `SeqCst` — глобальный порядок.
- **В примере:** `fetch_add(Release)` + `load(Acquire)` → **4000**.
- **Для простого счётчика** достаточно `Relaxed` — важен только **финальный результат**.
- **Пара `Acquire`/`Release`** создаёт **happens-before** — записи видны после чтения флага.
- **`SeqCst`** — когда нужен **тотальный порядок** или **лень думать**.
- **Правило:** используйте **минимально необходимый** ordering — `Relaxed` → `Acquire`/`Release` → `AcqRel` → `SeqCst`.
